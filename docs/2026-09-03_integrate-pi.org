* Goal

Give Pi the same shared instructions, skills, hooks, and session tooling as the
other supported coding agents on Linux.

The baseline does not include CLIProxyAPI routing, quota UI, general-purpose
MCP connectors, Claude workflow ports, or macOS. Those are separate optional
tasks below.

* Starting point

- [[file:shared/linux-home/pi.nix::1][shared/linux-home/pi.nix]] already installs Pi from
  ~pkgs.llm-agents.pi~.
- [[file:shared/linux-home/default.nix::15][shared/linux-home/default.nix]] imports Pi only on Linux.
- [[file:justfile::38][just update-ai]] already updates the ~llm-agents~ input, so it also updates Pi.
- [[file:shared/linux-home/pi.nix::1][shared/linux-home/pi.nix]] manages Ponytail,
  ~pi-agent-browser-native~, ~@tintinweb/pi-subagents~, and ~pi-web-access~ as
  unpinned Pi packages. Each live Home Manager activation installs or updates
  them.
- The same module installs the ~agent-browser~ executable through Nix.
- The package activation needs network access when it installs or refreshes a
  remote package.
- Skillshare publishes 37 shared skills through its universal
  =~/.agents/skills= target. Pi discovers that directory without a Pi-specific
  Skillshare target.
- Pi discovers project ~AGENTS.md~ and ~CLAUDE.md~ files without extra setup.
- ~pi-agent-browser-native~ 0.5.0 requires exactly ~agent-browser~ 0.34.0, so
  the Linux package stays pinned to that compatible browser version.
- ~@tintinweb/pi-subagents~ provides Claude-compatible ~Agent~,
  ~get_subagent_result~, and ~steer_subagent~ tools. It also provides the
  ~SubagentWorkflow~ tool for scripts that discover their fan-out at runtime.
  Release 0.19.0 requires Pi 0.84.0 or newer, and the managed Pi meets that
  requirement.
- The built-in ~Explore~ and ~Plan~ agents do not receive the write and edit
  tools. Their prompts forbid changes. They still expose Bash, so the runtime
  does not enforce read-only behavior.
- The extension enables ~SubagentWorkflow~ automatically. It stands down if
  another extension owns ~Workflow~ or ~SubagentWorkflow~, so the Nix setup
  does not force ~workflowsEnabled~ in =~/.pi/agent/subagents.json=.
- The extension does not enforce a confirmation before a workflow starts.
  Workflow children run with the tools of their selected agent type and the
  system privileges of the current user. Use workflows only for authorized
  work.
- ~pi-web-access~ provides ~web_search~, ~source_check~, ~fetch_content~, and
  ~get_search_content~. The Pi activation merges the Brave key from
  [[file:shared/secrets/brave-search.key][shared/secrets/brave-search.key]] into the mutable
  =~/.pi/web-search.json= while preserving other settings. The activation sets
  mode ~0600~ on the generated config.
- The activation reads the Brave key at runtime and does not interpolate it
  into its Nix derivation. The repository ignores this key so the flake source
  cannot copy it into the Nix store. Provision the local mode-~0600~ key file on
  each Linux host, and do not print it.
- The web package keeps its automatic provider order. Select
  ~provider: "brave"~ when the task must use Brave. Brave receives the search
  query and any domain or recency filters for that call.

* Upgrade the browser integration

~pi-agent-browser-native~ stays unpinned, so each live Home Manager activation
installs the latest npm release through Pi and Bun. The extension uses the
~agent-browser~ executable from ~PATH~ and validates it against one exact
capability baseline. Its wrapper relies on version-specific commands and output
shapes, so an independent newer ~agent-browser~ release can be incompatible.
The published ~pi-agent-browser-native~ 0.5.0 release targets 0.34.0, so
[[file:shared/linux-home/pi.nix::9][shared/linux-home/pi.nix]] fixes that version.

Use the extension target as the source of truth. Do not update the Nix package
to the latest independent ~agent-browser~ release unless the latest extension
targets it. The managed package source omits a version, so run this check before
the first activation after a new npm release. An activation that updates only
the extension can leave an incompatible pair.

1. Check the latest extension against the installed browser before changing
   the Nix pin:

   #+BEGIN_EXAMPLE
   nix shell nixpkgs#bun --command bunx \
     --package pi-agent-browser-native@latest \
     pi-agent-browser-doctor --skip-source-check
   #+END_EXAMPLE

   A passing result means the latest extension still targets the installed
   browser. Skip to step 4 when it passes. If the doctor reports ~expected X,
   found Y~, use ~X~ as the new Nix pin. Stop and investigate any other failure.

2. If the target changed, update ~agentBrowserVersion~, the nearby comment,
   and the ~fetchurl~ hash in
   [[file:shared/linux-home/pi.nix::9][shared/linux-home/pi.nix]]. Calculate the new hash with:

   #+BEGIN_EXAMPLE
   agent_browser_version=X
   nix store prefetch-file --json \
     "https://registry.npmjs.org/agent-browser/-/agent-browser-${agent_browser_version}.tgz" \
     | jq -r .hash
   #+END_EXAMPLE

3. Build the changed configuration without activating it:

   #+BEGIN_EXAMPLE
   just switch build
   #+END_EXAMPLE

4. Apply the configuration. The ~configurePi~ activation installs the latest
   unpinned ~pi-agent-browser-native~ release while the new Nix wrapper supplies
   its matching browser executable:

   #+BEGIN_EXAMPLE
   just switch
   #+END_EXAMPLE

5. Verify the installed versions, the compatibility baseline, and the browser
   runtime:

   #+BEGIN_EXAMPLE
   agent-browser --version
   jq -r .version ~/.pi/agent/npm/node_modules/pi-agent-browser-native/package.json
   ~/.pi/agent/npm/node_modules/.bin/pi-agent-browser-doctor --cwd /etc/nixos
   agent-browser doctor
   pi list
   #+END_EXAMPLE

   The Pi extension doctor must report a matching baseline and one active
   package source. ~pi list~ must show ~npm:pi-agent-browser-native~ exactly
   once.

6. Start Pi and make one ~agent_browser~ call with ~["--version"]~. Confirm
   that the tool returns the same version as ~agent-browser --version~.
