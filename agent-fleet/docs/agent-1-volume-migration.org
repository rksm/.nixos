* Approved scope

The user revised the original plan before the outage:

- Use a 250 GB volume.
- Stop services as needed.
- Exclude projects from the backup.
- Back up only unmanaged state, rather than a full disk or Nix store.
- Use a brief verification instead of a byte-by-byte comparison.

The backup excludes server snapshots and projects. The original home tree
was a rollback copy until the user approved its removal.

* Work completed

1. Created and attached the volume through OpenTofu. The plan added only the
   volume. Enabled Hetzner deletion protection and Terraform prevent_destroy.
2. Matched the new device to its cloud ID and size, then formatted it as ext4.
3. Made an initial copy of home while the source remained available.
4. Stopped Syncthing, user services, user sessions, and PostgreSQL. Both
   PostgreSQL clusters reported a clean shutdown.
5. Booted into Hetzner rescue. Confirmed the root filesystem was clean and
   mounted it read-only without journal replay.
6. Copied the final changes with rsync, preserving ownership, permissions,
   timestamps, hard links, symlinks, ACLs, extended attributes, and sparse files.
   Moved superseded initial-copy files into /home/.migration-precopy-extras.
7. Unmounted and remounted the volume. Compared file sizes, modification times,
   paths, links, permissions, ACLs, and extended attributes with rsync's dry
   run. The comparison returned no differences. No full content hashes were
   calculated.
8. Renamed the original home tree to /home.pre-volume and restricted it to root.
   Made the empty underlying /home mountpoint immutable. This prevents an old
   boot generation from filling it with replacement home directories.
9. Booted with user services and Syncthing disabled. Confirmed the volume UUID,
   user permissions, and project access. Ran Syncthing with peer networking
   blocked and checked its initial scan before reconnecting it.
10. Pinned the boot disk by its stable ID after Linux reordered the disk names.
    Installed GRUB onto the verified boot disk and completed a normal reboot.
11. Confirmed the required mount and service dependencies. Resumed the user
    services and the previously running PostgreSQL cluster. PostgreSQL accepted
    connections and a query returned four database entries.
12. Confirmed all four Syncthing folders were idle, with no pending files,
    pending deletions, or folder errors. Peer changes from storm arrived after
    reconnection. The benchmark browser-state deletions came from that peer.

* Cleanup and recovery

On September 11, 2026, the user confirmed deletion of /home.pre-volume and all
its contents. Before deletion, the cleanup checked both filesystem UUIDs. It confirmed the
directory type and rejected symlinks, mountpoints, and nested mounts. Only that tree was deleted. The independent state
backup on storm remains untouched.

After cleanup, the root disk has 97 GiB free, up from 39 GiB. The active /home
still uses volume UUID 939a3292-5c57-4954-bed2-de0c366990a4. The original home
rollback copy no longer exists.

For recovery, stop writers, preserve the latest volume data, copy and verify
that data onto the recovery destination, and then change the mount.

The underlying empty /home directory has the immutable attribute. In rescue,
with the volume unmounted, remove that attribute before replacing the mountpoint
for a rollback. Keep the volume intact throughout recovery. A saved old boot
generation alone does not restore current home data.

The new volume is not covered by a Hetzner server snapshot. This migration did
not add a scheduled backup policy. Syncthing remains synchronization rather
than an independent backup. The metadata checks passed, but they do not prove
byte-for-byte equality or guarantee against every possible storage failure.
